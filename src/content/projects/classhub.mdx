University students juggle class-specific discussions, course material, and study coordination across disconnected tools (group chats, email threads, shared drives) with no single space scoped to *this class, this semester.*

**ClassHub** is a real-time platform where every feature (chat, Q&A, file sharing, and study session scheduling) is scoped per class. Students browse and join classes via a live course-catalog integration, then collaborate inside class-specific feeds that update instantly for everyone enrolled.

### Architecture

<div class="my-8 space-y-4">
  <div class="p-5 bg-white dark:bg-gray-800 rounded border-l-4 border-blue-500">
    <div class="font-sans font-bold text-sm mb-2 text-black dark:text-white uppercase tracking-wide">Data Model</div>
    <div class="text-sm text-gray-600 dark:text-gray-400 font-serif leading-relaxed">Firestore is structured as <code class="font-mono text-xs bg-gray-100 dark:bg-gray-700 px-1 rounded">classes/{"{classId}"}/{"{chat|qa|sessions|resources}"}/...</code>, with nested replies and messages subcollections. Every piece of content is namespaced to its class rather than living in flat global collections, so isolating one class's feed from another is structural, not filtered client-side.</div>
  </div>
  <div class="p-5 bg-white dark:bg-gray-800 rounded border-l-4 border-green-500">
    <div class="font-sans font-bold text-sm mb-2 text-black dark:text-white uppercase tracking-wide">Real-time Sync</div>
    <div class="text-sm text-gray-600 dark:text-gray-400 font-serif leading-relaxed">All major views (chat, Q&A, session lists, in-session chat) subscribe via Firestore <code class="font-mono text-xs bg-gray-100 dark:bg-gray-700 px-1 rounded">onSnapshot</code> listeners rather than polling, so messages, votes, and replies appear instantly for every connected client. Firestore is configured with <code class="font-mono text-xs bg-gray-100 dark:bg-gray-700 px-1 rounded">persistentLocalCache</code> + multi-tab manager for offline support and fast reloads in production, with a long-polling fallback in local dev to work around a WebChannel/React 19 StrictMode double-invocation issue.</div>
  </div>
  <div class="p-5 bg-white dark:bg-gray-800 rounded border-l-4 border-orange-500">
    <div class="font-sans font-bold text-sm mb-2 text-black dark:text-white uppercase tracking-wide">Security Rules</div>
    <div class="text-sm text-gray-600 dark:text-gray-400 font-serif leading-relaxed">Firestore and Storage rules enforce access control server-side: authenticated reads, ownership checks on writes/deletes (<code class="font-mono text-xs bg-gray-100 dark:bg-gray-700 px-1 rounded">authorId == request.auth.uid</code>), and a default-deny fallback rule, with a 20 MB upload cap on Storage.</div>
  </div>
  <div class="p-5 bg-white dark:bg-gray-800 rounded border-l-4 border-purple-500">
    <div class="font-sans font-bold text-sm mb-2 text-black dark:text-white uppercase tracking-wide">Auth</div>
    <div class="text-sm text-gray-600 dark:text-gray-400 font-serif leading-relaxed">Passwordless email-link sign-in restricted to university email addresses, avoiding password management entirely.</div>
  </div>
  <div class="p-5 bg-white dark:bg-gray-800 rounded border-l-4 border-teal-500">
    <div class="font-sans font-bold text-sm mb-2 text-black dark:text-white uppercase tracking-wide">External Data Integration</div>
    <div class="text-sm text-gray-600 dark:text-gray-400 font-serif leading-relaxed">Course catalog data is pulled from a third-party academic data API (Paper.nu) through a Cloud Functions proxy (to dodge CORS and add caching headers), normalized client-side, and cached in <code class="font-mono text-xs bg-gray-100 dark:bg-gray-700 px-1 rounded">localStorage</code> with a schema-version key so stale shapes self-invalidate on the next fetch.</div>
  </div>
  <div class="p-5 bg-white dark:bg-gray-800 rounded border-l-4 border-gray-400">
    <div class="font-sans font-bold text-sm mb-2 text-black dark:text-white uppercase tracking-wide">Local Dev Workflow</div>
    <div class="text-sm text-gray-600 dark:text-gray-400 font-serif leading-relaxed">Full Firebase Emulator Suite (Firestore, Auth, Storage) wired into the app via hostname detection, so the team could develop and test against realistic backend behavior without touching production data.</div>
  </div>
</div>


### Design System

**Token system:** Built a custom design token system in Tailwind config rather than using default colors: a defined brand purple scale (`brand`, `brand-hover`, `brand-light`), semantic text/background/border tokens (`primary`, `sub`, `muted`, `line`, `subtle`), and purpose-specific border radii (`badge`, `btn`, `card`, `modal`, `avatar`) so spacing and rounding stayed consistent across cards, modals, and chips.

**Component patterns:** Reusable Tag/Avatar/badge primitives with a fixed semantic color palette (purple/teal/green/orange/pink/blue) deterministically assigned per user, so the same person's avatar color stays consistent across chat, Q&A, and session rosters.

**Layout:** Persistent sidebar (class list, navigation) + header + main content + contextual right sidebar, with modal-based flows (course discovery, create-session) layered on top via React Router's background-location pattern.


### My Role

As **Project Manager**, I led a team of student engineers through the full build, from defining the product scope and feature set to setting the technical architecture and reviewing the team's work into production.

I also worked hands-on in the codebase, building out the core Firebase layer: the per-class Firestore data model, passwordless email-link authentication, real-time chat/Q&A/study-session features, security rules for access control, and the deployment pipeline (Emulator Suite for local dev, Hosting + Cloud Functions for production).

We presented in **4 rounds** in front of industry representatives at the IEEE Technical Program final showcase.
